# Osborn PA 飞书版：独立审计报告

> 日期：2026-11-02（Asia/Shanghai）。审计人：本仓库实施代理（Claude Opus 5.5），单一模型。
> 性质：**独立审计意见**。不是 Garry Tan 本人意见，不是跨模型交叉验证，也不复用原 CEO／工程审阅结论；那两份是“技能角色审阅”，本报告逐项重新取证。
> 输入：原草案 D0.4、CEO 审阅、工程审阅（原文仅保存在本地不跟踪区域，含内部资源标识，不公开）；旧仓库只读源码；飞书官方资料；本仓库原型与一次真实 OpenAPI 探针。

## 0. 结论摘要

1. **方向成立，但有三处会改变实现路线的事实，原草案不知道：**
   - 飞书自定义插件（边栏插件、应用模式插件组件、仪表盘插件）默认是**开发者自行托管的网址**，只有上架插件市场后才可能由飞书托管。若不另找飞书托管位置，“工作台插件”路线与“不自建服务器”约束冲突。本机 lark-cli 已带妙搭（Miaoda）HTML／全栈托管命令，是需要实测的飞书托管候选。
   - Base OpenAPI 的 `client_token` **确实能让创建幂等**（本次真实探针证实）；但**更新没有任何版本检查**（探针证实：两个基于同一版本的写入都成功，后写覆盖）。插件 JS SDK 没有文档化的幂等参数。
   - 版本权益（官方价格页，2026-11-02 读取）：免费版／商业标准版每表最多 **2,000 行**、自动化 **200 次／月**；**行／列级权限从商业专业版起**。“多人、私有目标、时间块长期积累”的产品承诺实际要求客户使用专业版或以上。
2. **旧业务规则比草案描述的更复杂。** 旧系统有两条“目标→日程”路径：拖拽关联（保留目标、把目标截止日改为安排日期、目标与日程完成状态双向同步、归档目标时删除关联日程）与菜单转换（创建无关联日程并归档目标）。草案只把后者当“旧转换”，同时把前者的三个副作用静默去掉。需要用户决定（见 §4 决策 D-1）。
3. **评分算法可以无损移植。** 新规则包与旧函数在 20,000 组随机输入上中间量与结果 0 差异；唯一差异是旧代码遇到带时间的日期字符串会返回 null（压力 0），而飞书日期单元格是毫秒时间戳，新实现改为按时区换算并单独测试。
4. **“一个新核心 Base＋多张关联表＋三个入口”合理**，拆成三个 Base 没有收益。但“入口”需要应用模式页面，第二实例安装时应用模式页面与插件组件**目前没有可用的 CLI 复制路径**，安装交付要按“Base 复制＋应用页面手工／半自动重建”规划，直到证明有更好办法。
5. **当前可宣称的状态：** 文档完成；本地原型完成（75 项测试通过，真实浏览器内跨面板拖拽、刷新读回、同键重试不重复、版本冲突均已演示）；飞书实测仅完成一项 OpenAPI 幂等探针；**不能内部试用，不能跨企业交付。**

## 3. 对“一个核心 Base、多表、三入口”的审查结论

- **采纳。** 三个入口是应用模式中的三个页面（或页面组），不是三个 Base。目标中心与轻重缓急读同一张目标任务表；项目中心读项目表及相关人、复盘；工作台读目标与时间块。
- **拆分的唯一合理理由**是组织级隔离（例如个人目标必须对企业管理员不可见）。这需要每人独立空间，代价是项目—目标—时间无法原生关联、工作台需跨 Base 读取、权限和版本多处维护。当前没有证据表明用户需要这一点；PERM-02 已把语义写清。
